## 수동 확인 범위

Windows 그래픽 데스크톱에서는 `main_window_tests --capture-exclusion`으로 실제 화면 캡처를
추가 검사할 수 있습니다 (`QT_QPA_PLATFORM=windows`, `QT_MEDIA_BACKEND=ffmpeg`).
대기 상태에서 메인 창의 자홍색 표식이 보이는 것을 확인한 다음, 미리보기 상태로 전환해
제품 코드가 제외 설정을 적용하게 하고 뒤의 녹색 창이 연속 3프레임에 나타나는지 검사합니다.
중지 후에는 다시 원래 표식이 캡처되는지 확인합니다. Windows 10 버전 2004 이상에서 실행하세요.
화면 이미지는 저장하지 않습니다. 이 검사는 실제 데스크톱을 사용하므로 기본 CTest에서는 실행하지 않습니다.

`main_window`는 임시 INI 설정 저장소를 사용해 두 옵션의 기본값과 재생성을 통한 복원을 검사합니다.
offscreen 환경에서 화면/영역 겹침, 이동 후 미리보기 복원, 포털의 알 수 없는 대상,
권한 대기·시작 실패·종료·수동 최소화·최대화 복원 및 대체 동작의 일시정지/재개 명령을 검사합니다.
`main_window_startup_policy`는 화면 권한·공유 선택 중 창 유지와 인코더 시작 직전 최소화,
`main_window_move_into_capture`는 녹화 영역 밖에서 안으로 이동할 때의 일시정지 요청을 검사합니다.
실제 합성 영상 파이프라인 테스트는 녹화 준비 신호가 권한 승인·첫 프레임·출력 준비 후 한 번만 발생하고
미리보기나 재개 시에는 발생하지 않는지도 검사합니다.
이 검사는 macOS/Wayland 데스크톱의 실제 창 최소화·복원 타이밍 검증을 대신하지 않습니다.

macOS의 일반 CTest는 `offscreen` 플랫폼과 합성 프레임을 사용하므로 실제 Cocoa 창,
화면 기록 권한, 실제 화면·창·영역 캡처가 정상이라는 증거가 아닙니다.
macOS 변경 후에는 다음 절차도 확인합니다.

1. `./run-macos.command`로 `build/qt/ClipDock.app`을 실행하고 창과 입력 장치 목록을 확인합니다.
2. `도움말 → 권한 상태 확인`에서 실행 경로와 화면 기록 권한을 확인합니다.
3. 디스플레이·창·영역별로 미리보기를 시작하고 실제 화면이 갱신되는지 확인합니다.
4. MP4 녹화 → 일시정지 → 재개 → 저장을 실행하고 생성한 파일을 재생합니다.
5. `./scripts/package-macos.sh`가 출력하는 앱 경로도 별도로 실행합니다. 동기화 폴더의 경우
   로컬 임시 폴더에서 서명하며 자세한 경로는 [패키징 안내](packaging.md#macos)를 참고합니다.

화면 기록 권한이 거부되면 이를 성공으로 처리하지 않고 미검증 범위로 남깁니다.
새 ad-hoc 빌드는 기존 권한이 이어지지 않을 수 있으며 사용자 승인이 필요합니다.

Wayland 포털 승인 및 실제 마이크 입력은 그래픽 데스크톱에서 별도로 확인해야 합니다.
Windows 단축키는 아래 2026-10-29 데스크톱 기록에서 외부 앱 포커스와 OS 입력으로 확인했습니다.
물리 키보드 입력, macOS 단축키와 Wayland 데스크톱 승인 UI는 별도로 확인해야 합니다.
Windows 자동 테스트는 실제 등록과 `WM_HOTKEY` 메시지 전달을 검사하며 물리 키 입력을 대신하지 않습니다.
X11 테스트는 첫 입력, 보조 키를 놓은 상태의 오입력 차단, 겹친 단축키 이후의 정상 입력도 확인합니다.
Wayland 테스트는 창 활성화 토큰의 비동기 전달도 확인하지만, 실제 창 포커스 전환은 데스크톱에서 확인해야 합니다.
포털 테스트는 프로토콜과 앱 상태 처리를 검증하며 모든 데스크톱 백엔드의 동작을 보장하지 않습니다.
`main_window`는 저장 창 재진입, 모달 대화상자 및 파일 마무리 상태의 단축키 차단도 검증합니다.
Linux 단축키 테스트에는 `libxtst-dev`, `xvfb`, `xauth`, `dbus-daemon`이 필요합니다.
X11 자기 창 제외 통합 테스트에는 추가로 `openbox`, `xdotool`, `x11-utils`가 필요하며,
모두 설치된 경우 CTest에 등록됩니다. Linux CI에는 이 의존성을 포함합니다.
헤드리스 환경에서도 가능한 소프트웨어 MPEG-4 코덱을 사용하며 H.264 하드웨어 인코더 검증을
대체하지 않습니다.

## WSL X11 검증 기록 (2026-10-27)

검증 대상은 로컬 `5ff0ae9` 빌드입니다. WSL1 Ubuntu 20.04의 기존 격리 Ubuntu 24.04.4
환경에서 Qt 6.8.3, FFmpeg 7.1, Xvfb 1280×800, Openbox 3.6.1을 사용했습니다.
WSLg나 물리 Linux 데스크톱은 없으며, 화면 입력을 가짜 프레임으로 대체하지 않고 실제 X11 캡처를 사용했습니다.

| 항목 | 결과 |
| --- | --- |
| Release 빌드 및 CTest | 18/18 통과. X11 전역 단축키와 실제 화면 캡처 테스트 포함 |
| 겹친 미리보기 | 캡처에는 메인 창의 표식이 보이지만 UI의 동영상은 숨겨지고 중첩 방지 안내 표시 |
| 녹화 시작·재개 | 최소화 및 X11 창의 비표시 상태 확인 |
| 다른 앱에 포커스를 둔 단축키 | 별도 `xmessage` 프로세스에 포커스를 두고 XTest 입력으로 일시정지·재개·중지 확인 |
| 창 관리자를 통한 복원 | Openbox에 활성화를 요청하면 자동 일시정지. 재개 버튼을 누르면 다시 최소화 |
| MP4 저장·재생 | 소프트웨어 MPEG-4, 1280×800 영상 저장 및 전체 디코딩 성공. 종료 후 메인 창 복원 |
| 자기 창이 포함된 프레임 | **실패:** 두 번의 녹화에서 시작 부분에 각각 2프레임, 1프레임 검출. 두 번째 영상은 364프레임 중 배경 360프레임, 자기 창 표식 3프레임 검출 |
| Linux 배포 폴더 | 임시 경로로 복사하고 Qt SDK 관련 환경 변수를 제거한 뒤 실행 성공. XCB/Wayland/FFmpeg 플러그인 의존성과 X11 시작 검사 통과 |

두 번째 영상에서 자기 창 표식은 18.4ms, 5756.7ms, 5773.4ms에 검출됐습니다.
첫 번째는 녹화 시작, 나머지는 복원·일시정지·재개 전환 부근입니다.
Recording 상태에서 X11 창이 이미 비표시여도 저장 영상에는 이전 창 이미지가 남았습니다.
따라서 최소화 요청과 상태 검사만으로 캡처 파이프라인의 이전 프레임까지 차단되지는 않습니다.
창이 사라진 뒤 받은 프레임부터 인코딩하는 처리와 재개 시 프레임 처리는 후속 수정·검증이 필요합니다.
자기 창이 처음부터 전혀 들어가지 않는다는 기준은 통과 처리하지 않았습니다.

위 기록은 수정 전 `5ff0ae9`의 결과입니다. 2026-10-29 수정은 기존 Qt 캡처의 버퍼를
인코더에서 분리하고, X11 서버에서 창 상태 검사와 화면 취득을 함께 수행하는 별도 경로를 추가합니다.
시작·재개 및 차단 해제 시에는 네이티브 비겹침 확인 → Qt 다시 그리기 동기화 → 새 화면 재취득 순서로 처리합니다.
영역 경계는 실제 프레임의 잘라내기 좌표와 동일하게 계산합니다.
Openbox는 비합성 환경이며, 이 검사는 다른 프로세스의 배경 다시 그리기 완료나 합성 창 관리자의 잔상을 보장하지 않습니다.

재현 순서: X11에서 전체 화면 미리보기 → ClipDock 창 제외를 켠 상태로 녹화 → 자동 최소화 →
창 관리자에서 ClipDock 복원 → 자동 일시정지 → 재개 → 중지 → 저장 영상의 시작/전환 프레임 확인.
로컬 증거는 `.cache/wsl-desktop.P2xGUs/`, `.cache/wsl-desktop.iiFJer/`의 영상·로그·스크린샷,
전체 CTest 로그는 `.cache/self-capture-linux-ctest.log`에 있습니다.

검사 도구의 최초 실행은 외부 앱 포커스 명령 단계에서 중단됐고,
진단 출력을 추가하고 도구의 제한을 3초에서 10초로 늘린 뒤 위 동작을 두 번 확인했습니다. 제품 코드는 변경하지 않았습니다.
Wayland 공유/단축키 승인 UI, 실제 마이크, GPU 코덱, 물리 다중 모니터는 이번 검증에 포함하지 않았습니다.
배포 폴더 검사는 재배치된 앱의 실행·의존성을 확인하며, 녹화 검사는 동일 소스의 검증 실행 파일에서 수행했습니다.

## X11 자기 창 프레임 수정 (2026-10-29)

### Windows 정지 창 녹화 시간 원인 확인 (2026-10-29)

테스트 전용 Qt 창을 실제 `QWindowCapture`로 취득하고, 제품의 `configureRecorder`와
동일한 H.264·25 FPS·무음 설정을 사용했습니다. 각 조건은 녹화 상태 진입 후 6초 타이머로 중지했습니다.
전역 단축키, 자기 창 제외, X11 보호 캡처 경로 없이도 재현되므로 이 기능들이 재현에 필요하지 않습니다.

| 화면 조건 | 실제 녹화 상태 유지 | 저장 길이 | 디코딩 프레임 |
| --- | ---: | ---: | ---: |
| 정지 화면 | 5.995초 | 1.535초 | 47 |
| 약 3초에 한 번 색상 변경 | 6.000초 | 0.156초 | 6 |
| 100ms 타이머로 계속 변경 | 6.007초 | 5.991초 | 71 |

세 영상 모두 파일 끝까지 디코딩됐지만, 앞의 두 조건은 녹화 시간 보존에 실패했습니다.
정지 조건은 초기 프레임들이 들어온 뒤 마지막 약 4.5초간 새 프레임이 없었습니다.
한 번 변경 조건은 녹화 시작 후 약 3.057초에 파란 프레임을 수신했지만,
저장 영상에서는 해당 색상이 **0.139920초**에 나타났습니다. 마지막 정지 구간 누락에 더해
새 이미지의 표시 시각도 과거로 이동합니다. 계속 변경하는 조건만 정상 길이에 가까웠습니다.

원인 경로는 Qt 6.8.3 소스와 캡처/디코딩 로그를 대조하여 확인했습니다.

1. [Windows 창 캡처](https://github.com/qt/qtmultimedia/blob/v6.8.3/src/plugins/multimedia/ffmpeg/qffmpegwindowcapture_uwp.cpp)는
   새 텍스처가 없으면 프레임을 반환하지 않습니다.
2. [캡처 프레임의 시간 지정](https://github.com/qt/qtmultimedia/blob/v6.8.3/src/plugins/multimedia/ffmpeg/qffmpegsurfacecapturegrabber.cpp)은
   새 프레임의 시작 시각에 직전 프레임 취득 시각을, 끝 시각에 현재 취득 시각을 넣습니다.
3. [영상 인코더](https://github.com/qt/qtmultimedia/blob/v6.8.3/src/plugins/multimedia/ffmpeg/recordingengine/qffmpegvideoencoder.cpp)는
   시작 시각을 PTS와 녹화 시간 갱신에 사용하며, 프레임이 없는 마지막 정지 구간을 별도로 연장하지 않습니다.
4. ClipDock의 Windows 창 모드는 이 캡처 소스를 인코더에 직접 연결하고,
   UI 시간도 `QMediaRecorder::durationChanged`를 표시하므로 같은 문제가 노출됩니다.

수정 대상은 Windows 창 녹화의 프레임 시간 처리입니다. 실제 취득 시각에 맞는 이미지 표시,
새 프레임이 없는 정지 구간, 일시정지 제외 및 종료 시점까지의 길이 보존을 함께 검증해야 합니다.
이번 작업은 원인 확인이며 제품 수정은 아직 적용하지 않았습니다. 마이크 동시 녹음 및 다른 플랫폼으로
결론을 확대하지 않습니다. 낮은 평균 프레임 수 자체만으로 파일 손상이라고 판단하지 않습니다.

재현 소스와 실행 스크립트는 `.cache/desktop-validation-20261029/window-timing.cpp`,
`window-timing.ps1`이며 `-Mode static`, `-Mode pulse`, `-Mode animated`를 사용합니다.
각 `timing-*.log`는 실제 경과 시간과 원본 프레임 시각을, `timing-*.mp4.decode.log`는
저장 영상의 길이와 디코딩 결과를 기록합니다. `probe.ps1 -Video timing-pulse.mp4 -Frames`로
프레임별 시각과 표식 색상도 확인할 수 있습니다.
최초 진단은 제한 환경에서 캡처 오류가 났고, 실제 데스크톱 권한으로 재실행했습니다.
첫 재실행은 캡처 초기화 지연으로 15초 제한을 초과하여 무효 처리했으며,
60초 제한으로 다시 실행한 세 조건만 위 표에 포함했습니다.

## GitHub Actions

Windows·macOS·Linux 빌드 및 검사 워크플로는 [`.github/workflows/qt-build.yml`](../.github/workflows/qt-build.yml)에 있습니다.

한 대상이 실패해도 나머지 대상의 검사는 계속 진행합니다.

수동 실행의 `build_release`는 기본값이 `false`입니다. 켜면 해당 대상의 빌드·테스트가 통과한 뒤
배포 폴더 생성과 플랫폼별 바이너리 압축·업로드를 추가로 실행합니다.
사용법과 산출물 목록은 [패키징과 배포](packaging.md#github-actions에서-바이너리-생성)를 참고하세요.

OS 권한 승인과 실제 화면·오디오 캡처는 각 플랫폼에서 별도로 확인해야 합니다.

## macOS 로컬 실행 확인 (2026-11-02)

macOS 26.5.2 / Apple Silicon / 공식 Qt 6.8.3에서 확인했습니다.

- `./scripts/test-qt.sh`: 13개 테스트 통과.
- Cocoa 앱 실행, 실제 화면·창·640×480 영역 미리보기 확인.
- 사용자가 현재 앱의 화면 기록 권한을 다시 등록한 뒤 실제 캡처가 시작됨.
- H.264 전체 화면: 일시정지·재개·저장 후 AVFoundation으로 716프레임 모두 디코딩
  (1920×1080, 12.3초).
- H.264 영역: 지정한 640×480으로 저장 후 195프레임 모두 디코딩 (10.152초).
- 기본 경로 및 `PACKAGE_DIR=dist/qt`로 패키징·엄격 서명 검증 통과.
  생성한 ZIP을 동기화 폴더 밖에 풀어 서명 재검증 및 독립 앱 실행 확인.

초기 실측에서 25 FPS 설정과 달리 전체 화면 약 58.21 FPS, 영역 약 19.21 FPS가 확인되어
후속 수정했습니다. 화면·창·영역을 공통 프레임 입력 경로로 연결하고, 프레임 번호 기준의
고정 시각으로 저장합니다. 정지 화면에서는 마지막 이미지를 재사용하되 각 프레임의
시각 정보는 독립적으로 생성합니다. FPS 및 프레임 공유 회귀 검사를 포함한 **17개 테스트가
통과**했습니다. 현재 빌드 앱을 macOS 앱 목록과 화면 기록 권한에 다시 등록한 뒤,
실제 H.264 녹화 파일을 AVFoundation으로 전부 디코딩하여 다음을 확인했습니다.

| 녹화 대상 | 설정 FPS | 실제 FPS | 해상도 | 프레임 수 | 길이 |
| --- | ---: | ---: | --- | ---: | ---: |
| 전체 화면 | 25 | 25.0 | 1920×1080 | 221 | 8.84초 |
| 영역 | 25 | 25.0 | 640×480 | 181 | 7.24초 |
| 영역 | 60 | 60.0 | 640×480 | 554 | 9.234초 |

모든 프레임의 표시 시각이 `프레임 번호 / 설정 FPS`와 1ms 이내로 일치하고,
프레임 수를 파일 길이로 나눈 평균 FPS도 설정값과 0.1 FPS 이내로 일치했습니다.

`~/Movies/clipdock-fps25-region.mp4`, `~/Movies/clipdock-fps60-region.mp4`입니다.
